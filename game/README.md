# Oki Doki

**The Last Ticket** is the current playable episode of *Oki Doki*, an original, open-source psychological mystery set in Moonrabbit Arcade. Join Niko, Mira, Ash and a plush moth named Mallow for a homemade prize hunt with choices, player-written messages and four main outcomes. It is an unofficial, unaffiliated spiritual successor inspired by the emotional connection, surprise and player discussion associated with *Doki Doki Literature Club*; it does not use its characters, setting or game assets. The earlier radio episode, **After the Signal**, is retained in `src/story.js`.

## Desktop downloads

The Windows desktop preview requires Windows 10 or later on x64. It was exercised under Wine 11, but not on native Windows. The Linux x64 preview was tested on Ubuntu 24.04; its included local dialogue and transcription engines require glibc 2.34 or later, libstdc++ with GLIBCXX 3.4.30, OpenSSL 3 and libgomp. Other Linux distributions have not yet been verified. Each standalone desktop ZIP is portable: extract its entire folder and run the Oki Doki executable. See START-HERE inside the download.

Use an extractor that preserves Linux executable permissions, such as `unzip`. If permissions were stripped, open a terminal in the extracted `Oki-Doki-Linux` folder and run `chmod +x "Oki Doki" chrome-sandbox chrome_crashpad_handler local-ai/runners/linux-x64/llama-server local-ai/asr-runners/linux-x64/parakeet-cli`. This restores the app, its helpers and the two included AI runners.

## Play

You need Python 3 and a modern browser. From this directory, run:

```sh
python3 -m http.server 8765 --bind 127.0.0.1
```

On Windows, the Python launcher normally uses this command instead:

```powershell
py -3 -m http.server 8765 --bind 127.0.0.1
```

Open http://127.0.0.1:8765/ in your browser. Stop the server with Ctrl+C. If the port is already in use, choose another port in both the command and the URL. A local web server is required for browser JavaScript modules; opening `index.html` directly may not work.

The game includes a Kokoro voice model and prerecorded Kokoro clips for the fixed-text voice catalogue. With the bundled assets available, supported browsers can generate missing speech locally without a separate speech server. Alternatively, `python3 tools/play_local.py --port 8899` starts the game and an available Kokoro service; in AI settings choose **Use local launcher settings** and save. Existing text and transcription settings remain unchanged.

For the prepared Linux workspace, `python3 tools/play_local.py --with-mirid --port 8899` can start the game, the available local Kokoro service and an isolated Mirid profile for text. If the Parakeet runner and model are installed, the profile also enables transcription; otherwise text still works and the launcher leaves existing transcription settings unchanged. In AI settings, select **Use local launcher settings**, then **Save for this session**. When switching from `max_completion_tokens`, Mirid text presets select its supported `max_tokens` parameter; an explicit no-limit choice and the numeric limit remain unchanged. Add `--nano` to start Chatterbox Nano without a reference; your own file and speaker can be chosen later. See the [local service guide](voice-service/README.md) for requirements and other platforms.

The launcher defaults to the smaller Qwen2.5 1.5B model. If the workspace already has the 7B model and your machine can run it, add `--model Qwen2.5-7B-Instruct-Q4_K_M.gguf` to try it. The larger model needs more memory and may respond more slowly; either model can invent details. See the [local dialogue evaluation](MODEL_EVALUATION.md) for examples.

The opening is a fictional agreement screen: a pointer click anywhere moves its Agree button under the click and starts the story. Keyboard users can activate the focused button with Enter or Space. The interaction stores no agreement or tracking setting. With auto-read on, the opening is spoken after that first click, followed by the first passage. After each passage the speaker receives keyboard focus. Press Enter or Space to continue when the Continue button is available; use Tab to reach choices, text inputs and audio controls. Open **Recent story** beneath the dialogue to review up to 80 displayed passages, selected choices and submitted messages. It excludes unsent drafts and starts fresh on restart or resume. If a saved Mallow reflection contains a submitted message that did not receive a reply, that message is restored to Recent story with an unanswered label; the rest of the history stays in page memory rather than the checkpoint.

The entire story is playable without a network connection to an AI provider. Use **Save** during a passage to store a checkpoint on this device. To resume a saved story, open the game, pass the opening screen, select **Resume** in the top bar and confirm. You can also choose **Resume saved story** from the title screen after selecting **Restart**. Saving is optional: it records choices, submitted messages, the last displayed public reply, the player-written receipt annotation and bounded AI conversation context in browser local storage. It never saves AI endpoint settings or API keys. A completed AI conversation can be saved in place: its displayed response, up to 40 submitted review lines and bounded conversation and retry context are saved on this device. Unsubmitted drafts are not saved. A pending AI request cannot be saved; wait for the response or continue without waiting. Resuming a saved conversation shows the recorded response without requesting a new AI reply. If auto-read is enabled, its displayed text is spoken using the selected speech settings; a configured remote speech service receives that text. A very large checkpoint may be rejected without replacing an earlier save. **Delete saved story** removes the checkpoint. Restarting starts a new run but keeps the checkpoint until you delete or replace it. The Last Ticket uses a separate save key, so an earlier After the Signal checkpoint is not overwritten or loaded into the new story. The locally synthesized music-box loop and story cues start after the opening click; a quieter second layer changes with the scene. Use **Sound on** to mute them, or **Sound off** to turn them back on. Your choice is remembered on this device. The loop stops while the game is hidden and restarts when it returns. If your device keeps audio suspended, toggle sound off and on to retry. Speech is separate from the music and sound-effects control.

An [Android debug APK](dist/oki-doki-android-v247-debug.apk) is available for testing. Its build and five native unit tests passed. The source archive excludes APKs; obtain the debug APK separately, or follow the [mobile build instructions](mobile/README.md#generate-a-native-project) to build one locally. On an Android 11 software emulator with WebView 83, an earlier debug build exposed compatibility errors; v179 displayed the opening, restored a saved passage, reached the free repair-kit offer and played a suggested character message; a separate v179 emulator run sent free text to a synthetic local AI endpoint. In v180, voice previews and a story read-aloud request returned real Kokoro audio in the emulator, with audio output disabled. A v229 Android 11 emulator retry requested two distinct real Kokoro voices and a read-aloud, and reached a playing or finished status; emulator audio was disabled. The v227 Android debug APK passed two packaged WebView checks on an Android 11/WebView 83 software emulator: real touches reached the first choice, saved its response, recreated the activity and restored the passage; a separate seeded test touched all three screen pictures and checked the resulting fingerprint. A separate v227 test used Android touches and a synthetic endpoint to send a chat request and request distinct voice previews and read-aloud; real models, speech services and audible playback were not tested in that run. A native policy probe on an earlier build confirmed loopback permissions and two local HTTP connections. Physical Android gameplay has not yet been tested. The v242 APK predates the new bundled Kokoro inference, which has been tested in desktop Chrome, not yet in an Android WebView or on a physical phone. An iOS build still requires a Mac with Xcode, and iOS voice performance and compatibility are unverified.

## Install and offline play

The web game includes a progressive web app manifest and a service worker. On a browser that supports them, open the game over HTTPS (or localhost for development) and allow the initial page and assets to load; the browser may then offer an install or “Add to Home Screen” option. After the shell has been cached, the authored story can be opened without a network connection. Browser support, storage limits and installation steps vary, and a failed or cleared cache requires another online load. Opening the files directly with `file://` is not a supported way to install the app.

The worker caches public game shell files. For voices offline in the browser, open **AI settings → Speech → Download offline voices** while online. The optional download is about 170 MiB and requires an active service worker; if prompted, reload the game once first. The voice pack is separate for each installation and release, and browser storage may be evicted; prepare it again after an update or eviction. Native bundles already include the voice assets. The cache does not store player messages, API requests, microphone recordings or generated speech. AI dialogue requires a reachable configured text service; prerecorded clips and the local Kokoro engine do not require one when their assets are available. Story saving remains a separate, explicit feature. When a newer release is ready, **Update available — save first** appears in the header. Choosing it reloads the game; save a checkpoint first if you want to resume the current story. Older versions that do not yet have this control may require closing every game tab and reopening the game to activate an update. The PWA has not yet been installed or tested on an actual device. When changing a cached file for a release, update the cache version in `sw.js` so the browser can replace the previous shell.

## Optional AI dialogue

Many AI applications do not show users all of the system or developer instructions that shape a response; visibility depends on the service. Oki Doki’s own instructions can be inspected in `src/ai.js`, while a connected provider may apply additional instructions. This background is also available in AI settings, outside the story.

Each companion offers a choice between a personal discussion and a lighter conversation about your shared task. Both begin as private conversations, with a later choice about sharing a message. Conversation scenes offer suggested messages as well as a field for writing your own. When AI is configured, either sends the player’s words to that service. Without a service, each suggested message has its own written character reply; a typed message uses a general scripted reply. A suggested message’s matching written reply is also available if the request fails or the player chooses it instead. The scene indicates when dialogue will be scripted.

Open **AI settings** and supply the full URL of an OpenAI-compatible chat completions endpoint and a model name. For a local model, this might be `http://localhost:1234/v1/chat/completions`; the exact address and model depend on your server. An API key is only needed if the provider requires one. Under **Model compatibility**, select the output-limit parameter supported by your provider if the default fails. The response-token limit defaults to 100 and can be raised to 512, 2,048 or 8,192; selecting no output limit omits the parameter. Some models count hidden reasoning tokens against this limit, and larger limits may increase wait time and provider cost. For providers that reject a custom temperature, select **Provider default** under **Response variation**; the game then omits the temperature parameter. For example, the [OpenAI API documentation](https://developers.openai.com/api/docs/changelog?mw_entry=2026-09-03-3f56515da8b13ccc) says GPT-6 Astra does not support custom temperature. You can also change how long the game waits for a dialogue response (15 seconds to 2 minutes; default 1 minute), which can help slower local models. The endpoint must permit requests from the game's browser origin via CORS; remote providers must use HTTPS. The combined desktop handoff includes an optional local Qwen model: extract the complete handoff and desktop archive as described in START-HERE, then use **Start included desktop AI** and save the settings for the session. On Linux the bundled CPU runtime has been exercised; Windows and macOS execution have not yet been tested. Browser-only and phone builds do not bundle a conversational model. Model output-limit settings and availability still vary by provider; choosing a compatible temperature alone does not guarantee a model will work.

If a llama.cpp server reports that the conversation exceeds its context window, the game explains the issue. Increase the server’s configured context size if supported, or select a model with a larger window, then retry; the game does not silently remove the conversation to make it fit. Other providers may report the same problem differently and receive a generic error.

The companion you choose to speak with privately and Mallow can generate short responses. An optional later group conversation with Mallow has its own saved exchange; it does not send the earlier private or group conversation to the configured service. If you later talk privately with your companion, the last completed exchange with Mallow is included as a separate group conversation they heard. An unanswered submitted follow-up is saved separately and shown as unanswered in Recent story after resuming; it is not presented as Mallow’s reply. An optional conversation with the chosen companion also appears midway through the story, where the group can hear; its conversation history is kept separate from the earlier private exchange and Mallow’s conversation. The last completed exchange can be remembered in the companion’s later private conversation and is included in an explicitly saved checkpoint. The companion's request includes the witnessed setup for the selected shared activity, the chosen action and the companion's authored response, so the model has context for the moment you just played; the unchosen activity is not sent. In the later closing conversation, the selected action and reply use a separate bounded field so they do not crowd out the ending scene. After a successful AI response, the player may continue that conversation. With a service configured, the player may also edit or retry the first private message, including after an authored response; submitting a revision replaces that exchange in the current conversation and saved private context. Private follow-ups send the opening exchange and up to two recent exchanges to the configured service. Each history line is bounded to 700 characters, preserving the full 500-character player input and displayed AI replies. Mallow's shared follow-ups send the first and most recent shared exchanges, kept separately from the private conversation. If the player allows Mallow to repeat the last submitted private message to the crew, that one message is included in Mallow's first request and its bounded follow-up history. If there was no private follow-up, or the save predates this feature, the original message is used. Shared follow-up history stays in memory and is not saved in checkpoints. Declining keeps the private messages out of Mallow's model requests; the story establishes that Mallow heard the conversation. A temporary conversation review is available within an AI scene. Near the end, you may choose to speak privately with your companion again. Submitting that message sends your earlier private exchange, the new message, and brief authored context about the ending, evidence, companion’s closing line, the Mallow response and the search action you chose to the configured service. When present in the save and recorded in the reveal, the selected welcome-card and map-notice choices are also included. The companion’s witnessed personal disclosure and selected question and answer are also included when recorded in the save; older or inconsistent checkpoints do not invent them. If the player has visited the audit scene, the request also includes a brief summary of what the characters said and, when chosen, the player’s intervention. If the optional field-repair kit payoff was actually seen, its action is included in the chosen companion’s later private conversation. If Mallow helps after the lens was covered, its outcome reflects whether the player moved the covering or kept it in place; older or incomplete saves do not invent those choices. For the record ending, the request includes your selected response to Mira and her reply when that choice is present in the save. Longer context can exceed a local model server’s token window, depending on its configuration and the text. If no service is configured, the authored response is used. Mira is unavailable for this conversation if she remains downstairs. This exchange does not send your earlier private words to Mallow.

The story uses player preferences to select later authored responses and steer optional Mallow dialogue. In new runs, witnessed choices also shape the requested style of generated companion responses during private and shared-card conversations; a model may not follow it. This is runtime preference steering, not training a connected model. The story graph and outcomes remain authored. The game sends the relevant messages and a small scene and character description to the endpoint; a remote provider may retain the request according to its own policies. Configuration and credentials stay in page memory and are cleared on reload or close. For the first message, missing or invalid settings, a failed request or a timeout use an authored line. While that response is pending, the player can choose the written response. After the first generated reply arrives, the player can also switch it to the written line; subsequent follow-ups use the selected line as context. If a service is configured, the player can still send a follow-up after the first written response; the written line becomes part of that follow-up's context. Connecting a service while reading an offline written response also makes a follow-up and an edit-and-retry option available, without automatically sending a request. The retry replaces the original exchange and uses the conversation context from before that response. Changing chat settings cancels a pending response from the previous configuration. After a generated follow-up, the player can edit or retry their last message; a submitted revision replaces that exchange in the conversation history, and no retry is automatic. If a later follow-up fails, the last completed reply stays visible and the submitted message remains in that conversation’s bounded context; no unrelated written reply is substituted. You can edit or retry the message, or continue. Continuing without waiting also retains only your submitted message; a retry uses the context from before the failed attempt. Written alternatives apply to the first message, not arbitrary follow-ups. For generated replies over 700 characters, the game keeps text through the last likely sentence boundary within that limit or uses the authored line if none fits. When a response is cut off by a token limit, it may retain a clearly finished sentence before the cutoff. These checks are heuristic and can mistake an abbreviation for a sentence ending. Format checks reject some obvious narration, role confusion and repetition, but generated text can still be inconsistent or invent details.

### Experimental OpenAI Realtime read-aloud

The optional desktop companion can mint a short-lived OpenAI Realtime client secret when it has been explicitly configured with a server-side OpenAI key. See the [companion setup](companion/README.md). In **AI settings → Speech**, choose **OpenAI Realtime through companion**, enter its trusted HTTPS address and pairing token, and choose a Realtime voice such as `marin` for the narrator. The other speakers have distinct Realtime voices; if the narrator uses one of those voices, that speaker uses the narrator’s original `marin` voice. A speaker assigned the creator’s Chatterbox reference continues to use that reference instead. The companion preset also fills the address and pairing token without making a request. The normal speech service settings remain in use for microphone transcription.

When you select **Read aloud** or enable **Auto-read**, the game requests a short-lived client secret if it does not already have a usable one, then connects to OpenAI and buffers the generated audio for playback. It can reuse that secret for multiple spoken segments and passages using the same companion and pairing token, but will not reuse it within five seconds of the returned expiration. Secrets are kept only in memory, cleared when speech settings are opened or changed or when synthesis fails, and never saved. This can incur OpenAI charges; the standard OpenAI key stays on the companion. Pairing and voice settings remain in memory for the session. Realtime is a generative model and can change or add words even when asked to read exactly. Browser WebSocket, actual provider response, physical playback and mobile operation have not been verified. Consult [OpenAI’s Realtime connection guidance](https://developers.openai.com/api/docs/guides/voice-websockets?api=realtime) and [browser authentication guidance](https://developers.openai.com/api/docs/guides/voice-webrtc?api=realtime) for current behavior.

## Included desktop transcription

For the Windows and Linux desktop package, open **AI settings → Set up included AI and microphone**, then **Save for this session**. This starts the included local character model and selects the included local transcriber when no custom transcription service is configured. A custom transcription service is left unchanged, as are separately configured voices. Setup never starts recording; choose **Record a reply** in a conversation when you want to use the microphone. You can still configure either component separately using the controls below.

The Windows and Linux desktop downloads include a local Parakeet transcription model. To use it, open **AI settings → Speech → Use included desktop transcription**, then save settings for the session. The action does not start recording: use **Record a reply** in a conversation to capture a message. Transcription runs on the computer and fills the reply field; the player can edit it before sending. The model is English-language, and recognition can be wrong. Linux was tested with a synthetic microphone recording; the Windows runner was tested under Wine, not on native Windows. Browser-only play still needs a compatible speech service for microphone transcription.

## Mirid and speech

1. Start the installed Mirid backend and load a text model in Mirid. Open the game through a loopback HTTP server as described above; opening it directly as a file will not work.
2. Open **AI settings**. The default Mirid backend is `http://127.0.0.1:8000`; adjust the port if your installation uses another address. **Use Mirid for text and speech** fills in the text and speech addresses. Then **Check available models** reads advertised model and voice information without loading a model; local model IDs can be selected in the model field or entered manually. Advertised does not mean ready. Load a text model in Mirid and save the settings for the session.
3. If Mirid uses the opt-in Linux API profile with experimental local speech, select **Mirid Linux single-voice speech (experimental)**. This uses the local Parakeet transcription route and the local Kokoro status/probe and WebSocket routes. The probe runs only when you request speech and the voice is not ready; the experimental voice is fixed to `af_heart`. These routes require the corresponding Mirid experimental features and verified assets to be enabled. The ordinary Mirid desktop mode uses `/transcribe` and `/tts`.
4. For voice input, choose **Record a reply** beside a reply field, allow microphone access, then choose **Stop recording and transcribe**. The game records at most 60 seconds as mono 16 kHz PCM WAV, compatible with Mirid's local `parakeet-cpp:tdt_ctc-110m:q4_k` route as well as its standard engines. Check and edit the transcription before submitting. Configure the exact installed Mirid ASR engine in settings; model availability depends on your Mirid installation.
5. **Read aloud** voices the current passage and visible story choices and prompts. **Auto-read** is on for a fresh install and follows passages as you advance; its on/off choice is remembered on the device. **Auto-advance** is off by default; switch it on to continue automatically after each completed spoken passage. It waits for you at choices, inputs, AI exchanges and endings, and stops if speech is stopped or fails. The opening is queued after the first click, then the first scene is spoken. Matching prerecorded clips play first. For other text, the default Kokoro service is tried if available, with the bundled on-device Kokoro model as fallback; an explicitly selected separate service or Chatterbox/Realtime voice remains in use. If story sound is enabled, auto-read waits for the scene cue; **Read aloud** interrupts it. **Stop audio** stops playback, recording or pending work and turns auto-read off. Opening settings also stops current voice activity. When a service is used, it receives the speech text; local inference stays on the device. If speech fails, auto-read turns off for the session and can be retried. No microphone recording starts automatically.

Long Chatterbox Nano passages are requested in ordered parts, with the next part prepared while the current one plays. This can start speech sooner; there may still be a pause between parts. If the browser blocks a part, **Play ready audio** retries it. Stopping prevents later parts from playing, though a local model may finish the inference already in progress.

Authored spoken lines inside a narrated passage use the corresponding character’s configured voice; printed quotations and player-supplied text remain with the passage speaker. A mixed passage can require several sequential speech requests, so service latency and provider charges may increase. In speech settings, **Faster: prepare two parts ahead** is optional and can reduce pauses; stopping or advancing early can send an extra request that your provider may charge for. The default prepares one part ahead. The seven default Kokoro voices are bundled for local inference. The creator’s personal Chatterbox reference and any shared Chatterbox service are not configured yet.

If transcription and read-aloud run at different addresses, keep the transcription address in **Speech service base URL** and enter the TTS address in **Read-aloud service URL**. Leaving the latter blank uses the speech service address for both. A separate read-aloud service has its own optional key and does not receive the transcription service key. Set **Read-aloud service protocol** if the TTS endpoint uses a different protocol, such as Mirid-compatible /tts for the optional multi-voice Kokoro service while transcription remains in Mirid Linux local speech mode. The optional Chatterbox reference setting has a separate address for its selected speaker.

For the creator’s one shared Chatterbox voice, an independently recorded reference and a speaker can be chosen later. The ordinary player interface does not ask players to supply a reference. For a local audition, open `http://127.0.0.1:8766/?voice-creator=1` (replace the port if needed), then use **AI settings → Speech → Creator voice audition** to select a reference file or an existing service reference, choose one speaker and preview it. This is a session-only audition; it does not publish a voice for other players. Once the creator has chosen a speaker and configured a compatible public service, the build can assign that one voice for everyone as described in [publisher voice setup](voice-service/PUBLISHER-VOICE.md). All other speakers retain their separately configured voices. Neither a publisher service nor the creator’s reference is configured yet. Chatterbox Nano, Faster and Turbo require a compatible running service; no reference recording or voice-cloning model is bundled. Real-reference quality and device behavior remain untested.

In **Speech**, choose a speaker under **Preview a speaker** and select **Preview voice** to hear a short sample using the settings currently displayed, before saving. The preview uses the assigned Chatterbox reference for its one selected speaker and the configured voice service for other speakers. It sends the sample text to the selected service and stops when settings are changed or closed. If playback is blocked, select **Play ready audio**. Previewing does not save the settings.

The speech settings can instead target an OpenAI-compatible API; set its base URL, models, voices and optional key. The initial speaker voice values are distinct Mirid Kokoro IDs. With a Mirid-compatible Kokoro read-aloud service or the selected phone companion’s Kokoro service, an empty speaker field uses that speaker’s Kokoro default; other speech protocols use their own default. Replace voice IDs with values your provider supports; for example, OpenAI lists `alloy` for `tts-1`. OpenAI has [announced shutdown on January 6, 2027](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create) for `tts-1` and its other listed Speech API TTS models. Its recommended Realtime replacement uses the separate experimental companion-based option described above, not this HTTP speech adapter. Other compatible providers set their own model and voice availability. For Mirid, set the Mirid engine IDs and Kokoro voice IDs configured in that installation. Remote APIs may have different models, supported voices and charges. Audio and requested text are sent to the configured service when the player chooses the corresponding control, including subsequent passages while auto-read is on; their handling depends on that service. To use desktop Mirid from a phone, see the optional [companion setup](companion/README.md). The browser may request microphone or local-network permission. Mirid does not need its global origin settings changed: use a localhost origin allowed by the installed backend. A browser's permissions and CORS policy still apply. The game itself does not start, install, load or manage Mirid or its models; the optional local launcher can start an isolated workspace profile.

## Design, artwork and limitations

The Last Ticket is a first vertical slice rather than a complete game. It includes three companion routes, different discoveries and four main outcomes. Each route offers a playful invitation or a team-focused alternative; an accepted invitation may be recalled later. When AI dialogue is enabled, the selected companion’s witnessed relationship choice and answer are included in that companion’s private dialogue context. A written follow-up topic with a companion changes a later rescue action on one route. Mira can remember an optional name the player gives a drawing, including after save and resume. The last completed public reply from Mallow, whether generated or written, can reappear later and be used in a player-selected action; the game does not infer a branch from its meaning. Conversation context is bounded rather than persistent model memory. The fixed voice catalogue entries are supplied as generated Kokoro recordings; passages containing runtime values may require live synthesis. There is no full soundtrack. Desktop browser playtests have reached endings on each companion route, although not every combination of choices has been played in a browser. See [PLAYTEST.md](PLAYTEST.md) for what was and was not tested. An Android debug APK has been built and its five native unit tests passed. An Android 11 emulator test reached the opening, restored a saved passage, reached the free repair-kit offer and played a suggested character message; physical phone compatibility and an iOS build remain unverified.

The arcade, cushion-fort hideout, sewing room, stair landing and playroom images (`assets/arcade.png`, `assets/hideout.png`, `assets/sewing-room.png`, `assets/stair-landing.png`, `assets/playroom.png`) and the Niko, Mira, Ash and Mallow portraits (`assets/niko.png`, `assets/niko-concerned.png`, `assets/mira.png`, `assets/mira-concerned.png`, `assets/ash.png`, `assets/ash-concerned.png`, `assets/mallow.png`, `assets/mallow-concerned.png`) were generated as original artwork for this project using the built-in image-generation tool. The dim playroom (`assets/playroom-dark.png`) was edited from the existing playroom image with the same tool; its instructions are recorded in `assets/PLAYROOM-DARK-PROMPT.md`. The closing fort shadow (`assets/hideout-shadow.png`) was edited from the existing hideout image; its instructions are recorded in `assets/HIDEOUT-SHADOW-PROMPT.md`. The sewing-room, stair-landing and alternate portrait prompts are recorded in `assets/SEWING-ROOM-PROMPT.md`, `assets/STAIR-LANDING-PROMPT.md`, `assets/NIKO-CONCERNED-PROMPT.md`, `assets/MIRA-CONCERNED-PROMPT.md`, `assets/ASH-CONCERNED-PROMPT.md` and `assets/MALLOW-CONCERNED-PROMPT.md`. The two images in `concepts/` are generated exploratory moodboards, not final locations.

The six `assets/souvenir-*.svg` illustrations are original project-drawn vector art used for the route-specific card. The three `assets/screen-signal-*.svg` drawings are original vector art for the chosen signal on Mallow’s screen.

`assets/studio.png`, `assets/noor.png` and `assets/ellis.png` are generated artwork retained from the earlier radio prototype. The earlier signal icon is retained with that prototype. Mallow's new launcher artwork (`assets/mallow-icon-original.png` and its resized variants) was generated from the Mallow portrait using the built-in image-generation tool. The launcher assets have not been visually checked on a native device.

These suites exercise story routing, save/resume, model fallback and cancellation, mocked speech/discovery contracts, WAV capture, the companion gateway, service-worker cache policy, native staging and app event wiring with a simulated DOM. They do not replace testing in a real browser, with live providers or on mobile devices.

For this workspace, `tests/mirid-live-smoke.py` exercises the actual game adapters against an isolated Mirid backend using an existing local text model, a synthetic speech fixture and local Kokoro. Add `--gateway` to exercise the HTTPS phone companion as well, or `--long-speech` to exercise direct multi-part Kokoro speech; the latter can take several minutes on CPU and cannot be combined with `--gateway`. It requires the existing Mirid runtime/assets, Python with httpx and Node 22+ for direct mode. Gateway mode requires Node 24+ and OpenSSL, as described in the companion guide. See the script header and `--help` for paths and options. It does not access a physical microphone or speaker or test a browser or phone.

## Standalone web package

From this directory, `python3 tools/package_web.py` creates `dist/oki-doki-web.zip`. On Windows, use `py -3` instead. The archive has `index.html` at its root and contains the web game and assets; it does not include the mobile projects, a text-generation model or a separate speech service; it does include the bundled Kokoro speech model and any recorded clips present in the assets. Unpack it into a directory and serve that directory over HTTPS, or localhost for a local test. A static host can serve it from a subdirectory as long as the extracted paths are kept together; the installable app and service-worker scope stay within that directory. Opening the extracted `index.html` as a local file is not supported.

For a local smoke test, unpack the archive and run `python3 -m http.server 8765 --bind 127.0.0.1 --directory /path/to/extracted-web-game`, then open `http://127.0.0.1:8765/`; on Windows use `py -3`. Choose another port if necessary. Run `python3 tests/package-web.test.py` to check reproducibility and contents. The package is a prepared artifact, not a published site. AI dialogue needs a configured, reachable text service. Recorded clips and bundled Kokoro speech can work without a speech service on supported devices when their assets are available; other selected speech services require a reachable endpoint. Remote services are subject to HTTPS and CORS policies.

The archive contains the web source, tests, companion and native project sources; it excludes installed dependencies, generated web bundles and build outputs.
